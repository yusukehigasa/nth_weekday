# 共通の開発ループ

通常モードとオーケストレーターモードに共通する、1件の変更の反復・停止・再開を定義する。ルートの AGENTS.md、HUMAN_IN_THE_LOOP.md、CODING_RULES.md を優先する。オーケストレーターモードの工程と担当は [orchestrator.md](orchestrator.md) に従い、本書で別のモードや委譲許可を追加しない。

## 開始と記録

1. 目的、受け入れ条件、対象外、担当・編集範囲、検証方法を短く明確にする。仕様を決定できない場合は HUMAN_IN_THE_LOOP.md に従う。
2. 編集前に作業ブランチと既存差分を確認する。Issue の有無による命名は AGENTS.md に従う。
3. 修正・検証の上限と記録場所を決める。通常の短い作業は会話内の記録でよい。承認待ち、中断、担当への引き継ぎ、複数セッションにまたがる作業、導入試行では [作業記録テンプレート](../templates/task-record.md) の項目に沿って、次節の保存先に記録する。
4. 通常モードでは実行担当、オーケストレーターモードでは親が記録を管理する。子は証拠と次の行動を親へ返す。read-only の担当はファイルを書かない。

## 記録の保存先と寿命

- Git管理するのは共通仕様とテンプレートなどの再利用する知識。タスクごとの進捗・検証ログ・承認待ちの状態はコミットしない。
- 永続化が必要な場合の既定は、Git管理対象外の `.codex/task-records/<日付>-<タスク名>.md`。通常モードは実行担当、オーケストレーターは親が必要に応じて作成する。テンプレート自体に進捗を書き込まない。Gitで共有されないため、別端末・別checkoutで参照できるとは限らない。
- 担当者や端末をまたいで共有する場合は、ユーザーが明示したIssue・Notion等を保存先にできる。作成・更新は HUMAN_IN_THE_LOOP.md の外部投稿ルールに従い、投稿先と内容が明示的に依頼された範囲で行う。PR作成の依頼だけで、別のIssue・Notionへの継続的な記録投稿を始めない。
- タスクごとに正本の場所（ローカルパスまたは外部URL）を1つ決め、会話・引き継ぎで伝える。外部保存ではテンプレートの項目を本文やプロパティに対応させ、リポジトリ固有の相対リンクはそのまま転載しない。ローカルと外部で同じ状態を二重管理しない。
- 保存先を移す場合は最新状態を引き継ぎ、正本の変更を伝える。外部投稿の許可がない・参照できない場合は、ローカルへの切替を明示して記録を維持する。共有に依存する引き継ぎは、受け手が参照できる方法が整うまで完了扱いにしない。
- 記録は作業中・再開用であり、完了後の長期保存は必須にしない。最終結果・検証の要点・未解決事項は会話や依頼されたPR等で共有する。ローカル記録は必要な引き継ぎや試行評価を済ませた後、作業者が削除できる。自動削除や外部記録の削除は行わない。
- 再利用する知見はspec・開発ルール・文書へ整理して反映する。記録をそのままGitへ取り込まない。導入試行の評価も同じ保存方針に従う。

## 反復と判断

1サイクルは、1つの受け入れ条件または原因に対する修正と、その検証結果の判断までとする。調査・コマンドの個々の呼出しを1サイクルとは数えない。振る舞い変更は先に失敗する spec を確認し、最小実装で通す。設定・文書のみなら CODING_RULES.md の対応する検証を使う。

| 結果 | 行動・状態 |
| --- | --- |
| 実装に起因する検証失敗 | 原因・根拠・次の仮説を記録し、許可された範囲で修正して再検証する（実行中） |
| 依存不足・環境障害 | 環境を診断し、許可された範囲で復旧する。無関係な実装を変えない。復旧できなければ阻害要因を記録する（阻害） |
| 利用者への影響が異なる未決仕様、未承認の操作・委譲 | 選択肢と必要な判断を示し、依存する作業を止める（判断待ち） |
| 必要な検証と受け入れ条件を満たす | 通常モードは差分を自己確認する。オーケストレーターは承認を得て独立レビューへ進む |
| 停滞または上限到達 | 原因、試行済みの方法、残課題、次の選択肢を報告し、当該タスクの自動反復を止める（上限・停滞停止） |
| すべての完了条件を満たす | 完了として証拠と限界を報告する |

独立レビューの Blocker / Major は解消する。Minor / Nit は非阻害として扱い、好みだけで反復を延長しない。根拠のない指摘は親が整理する。通常モードの自己確認を独立レビューと記録しない。

## 上限と承認

- 初期値はタスク全体で最大3サイクル。同じ原因で2サイクル続けて新しい証拠・仮説・改善が得られなければ停滞として止める。これは試行用の値であり、品質や最適性を保証しない。3サイクル目で全完了条件を満たした場合は完了とし、未達の場合に上限停止する。
- 担当交代、再委譲、セッション再開で回数をリセットしない。時間・費用の上限が指定されていればそれも守る。指定がなく取得できない費用は「未計測」とし、推測で埋めない。
- 上限到達後に続ける場合は、原因分析と新しい方針・上限を提示し、ユーザーの明示的な継続指示を記録する。承認待ちの経過時間を承認や進展とみなさない。
- 承認済みの担当が、同じ工程・範囲内で修正と検証を反復するための追加承認は不要。新工程、差し戻し後の再委譲、担当・範囲変更は HUMAN_IN_THE_LOOP.md に従い、直前に承認を得る。
- 承認待ちでは依存しない調査・準備のみ進められる。未承認の委譲や操作を開始しない。外部投稿の許可は別に確認する。
- テスト削除、期待値の弱体化、検証の省略、受け入れ条件や承認ルールの変更によって成功扱いにしない。必要な仕様変更は理由と影響を示し、既存の承認条件に従う。

## 検証の証拠

検証ごとに、対象、実行時点のファイル状態、環境、コマンド、成功・失敗・未実行、結果の要点を対応づける。ログ全文や秘密情報は記録しない。

- ファイル状態はブランチ、基点の commit、関連する追跡済み・未追跡ファイルの一覧と内容の識別情報で示す。作業ツリーに変更がある場合、HEAD だけを検証の識別に使わない。
- 初期運用では、検証対象ファイルの SHA-256 一覧などを記録する。RSpec なら実装・spec・依存・実行設定も対象に含める。記録自身は対象から除外し、記録の編集だけでコードの検証を無効化しない。
- Ruby の検証では Ruby・Bundler と依存状態を記録する。文書のみなら使用した検証ツールを記録し、Ruby 環境は対象外と明記してよい。
- 関連ファイル、依存、実行環境、受け入れ条件が変わった場合は影響する検証を再実行する。同じ状態で成功済みの検証は、追加変更・失敗・未解決の懸念がなければ再実行しない。
- テスト成功は受け入れ条件の確認を代替しない。独立レビューも対象差分に対応づけ、レビュー後の変更は影響範囲を再確認する。再委譲が必要なら承認を得る。

## 中断と再開

中断・判断待ち・阻害・上限停止では、現在の工程、累計サイクル、承認の根拠と範囲、残課題、次の行動を保存する。承認の記録は参照情報であり、それ自体が許可を発生させるものではない。確認できない承認を推測で補完しない。

再開時は、記録と実際のブランチ・基点・差分・対象ファイル・実行環境を照合する。他者の変更を戻さない。不一致があれば影響を調べ、古い検証結果やレビューを無条件に流用しない。別工程や別範囲に過去の承認を流用しない。上限・停滞停止からの再開には、前節の継続指示を確認する。

## 完了と試行評価

受け入れ条件、変更に適した検証、必要な文書更新、差分確認が揃った場合のみ完了とする。オーケストレーターでは独立レビューの重大な未解決事項がないことも必要。未達・阻害・判断待ち・上限停止は完了と区別する。PR は依頼された場合のみ扱い、ローカル完了と公開・マージを区別する。

導入後3〜5件を試行として記録する。タスクの種類・規模、サイクル数、人間の介入回数と理由、可能なら実作業時間・待ち時間・費用、手戻り、記録負担を残す。介入回数は承認・判断の回答1回を1件とし、必須承認と仕様相談を分ける。未計測値をゼロ扱いしない。

誤った完了宣言と承認違反がないことを優先し、同程度の従来タスクと比較できる場合に限り改善傾向を見る。比較データがなければ基準値の収集とし、速度改善を主張しない。繰り返す失敗は spec・検証・workflow の改善候補として残す。手順改善は別タスクで評価し、進行中の完了基準を都合よく緩めない。

この段階では定期実行や検証の自動収集を必須にしない。試行結果から必要性を判断し、CI・承認方針の変更には既存の承認条件を適用する。
