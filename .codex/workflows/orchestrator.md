# Development Orchestrator

## 共通ルール

- 開始時に作業規模を判断し、小規模なら通常モードで進められる理由と範囲を提示してユーザーに確認する。同意前には切り替えない。
- 親が要件・計画・実装・独立レビューを順に管理する。各工程の結果を次へ渡す。サブエージェントへの委譲前には `HUMAN_IN_THE_LOOP.md` の承認ゲートを必ず通す。
- 軽い要件整理と計画は親が該当 role を読んでまとめてよい。複雑な論点は委譲する。
- 独立した調査は並列化し、同じ調査を重複させない。完了した調査担当は関連する追加調査に再利用する。
- 実装は必ず別エージェントに委譲し、レビューは実装担当以外に委譲する。
- 子は再委譲しない。同時実行は設定上限以内で必要な数だけ使う。
- 同じ checkout を共有する。親がブランチ・worktree・commit・push を調整し、子は勝手に切替・同期・commit しない。他者の変更を戻さない。編集前にルート `AGENTS.md` の命名規則で作業ブランチを作成・確認し、main 上では編集・コミットしない。
- 委譲時はユーザーが承認した工程・担当・範囲、目的、受け入れ条件、所有ファイル、前工程の要点、検証方法を渡す。並列の書込みは所有範囲を重複させず、他の作業者がいることを伝える。

## Role の選択

| 工程 | Profile | custom agent | fallback |
| --- | --- | --- | --- |
| 要件 | `../agents/issue-manager.toml` | `issue_manager` | `default` |
| 計画 | `../agents/planner.toml` | `planner` | `explorer` |
| 実装 | `../agents/implementer.toml` | `implementer` | `worker` |
| レビュー | `../agents/reviewer.toml` | `reviewer` | `explorer` |
| PR（依頼時） | `../agents/pr-manager.toml` | `pr_manager` | `worker` |

custom agent が使えなければ利用可能な built-in agent に対象 TOML を明示的に読ませ、同じ役割を渡す。表の fallback もなければ `default` を使う。read-only の役割は編集しない。稼働中セッションの古い profile は再読だけで上位の指示が置換されるとは限らないため、新しいセッションまたは fallback を使う。

## 工程

1. **要件整理**: ユーザー依頼や既存 Issue から目的・受け入れ条件・対象外を明確にする。Issue がなくてもローカル要件で進める。Issue の作成・更新はその外部投稿を明示的に依頼された場合だけ行う。要件整理を委譲する場合は、担当・範囲・完了条件を提示してユーザーの承認後に開始する。
2. **計画**: 関連実装とルールを調べ、変更対象・手順・検証・リスクをまとめる。通常の設計判断は根拠を示して進め、`HUMAN_IN_THE_LOOP.md` に従って操作の許可を確認する。計画を委譲する場合は、要件整理の結果と担当・範囲・完了条件を提示してユーザーの承認後に開始する。
3. **実装**: 計画・担当・所有範囲・完了条件を提示してユーザーの承認後に委譲する。編集前に作業ブランチを確認する。振る舞い変更は TDD、設定・文書変更は `CODING_RULES.md` に従う検証を行う。計画から外れる大きな変更は親に戻す。
4. **独立レビュー**: 要件・計画・差分・検証結果とレビュー担当・範囲・完了条件を提示し、ユーザーの承認後に実装担当以外へ渡す。根拠ある指摘を確認し、重大な問題は実装に戻して修正後に再レビューする。
5. **PR（依頼された場合のみ）**: レビュー後に投稿範囲・ブランチ・検証結果・担当・完了条件を提示し、ユーザーの承認後に委譲する。関連 Issue はある場合だけ参照する。外部投稿を依頼されていなければ、この工程は不要。

## 完了と報告

要件を満たす変更、変更に適した検証、独立レビューで重大な未解決事項がないことを確認して完了する。ローカル変更の依頼は Issue / PR がなくても完了できる。

変更点・理由・検証結果・レビュー結果・未検証事項を簡潔に報告する。Issue / PR がある場合は URL を添える。必須事項が未完なら、完了とはせず阻害要因を明記する。
